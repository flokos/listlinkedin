# 09: API design

V2's HTTP API lives under **`/api/v2/`** and is built from DRF **ViewSets**
([ADR-010](adr/ADR-010-viewsets-and-api-v2.md)). V1's `/api/v1/` stays during the transition
(see [v1 compatibility](#api-v1-during-the-transition)). The OpenAPI 3 schema is generated by
drf-spectacular at `/api/schema/?version=v2`, with Swagger at `/api/docs/` (V1 setup, extended
per version).

## Conventions

| Topic | Rule |
|---|---|
| Format | JSON in and out (V1 parsers and renderers). `multipart/form-data` only on the upload endpoints |
| Identifiers | Lists by `public_code` (`{code}`), groups by `code`, links by UUID, revisions by `number`, members by user id. UUID `id`s are returned but are never needed in URLs except for links |
| Authentication | Django session cookie (`sessionid`, `HttpOnly`, `Secure` in production, `SameSite=Lax`) with **CSRF** on unsafe methods (`X-CSRFToken` header from the `csrftoken` cookie [R8]). Legacy lists also accept `Authorization: Bearer <owner token>`, which needs no CSRF because it isn't ambient |
| Authorization | [12-AUTHORIZATION.md](12-AUTHORIZATION.md). Not viewable → 404. Viewable but forbidden → 403. Account required → 401 with `WWW-Authenticate: Session` (`Bearer` on endpoints that also accept legacy owner tokens) |
| Pagination | `PageNumberPagination` shape `{count, next, previous, results}` (V1-compatible). Default 20, max 100. A list's links default to 100 per page, which is the whole list |
| Ordering and filtering | `?ordering=` on collections where documented. `?q=` and `?tags=a,b` on the directory |
| Versioning | URL path. `/api/v1/` is frozen and deprecated (`Deprecation` and `Sunset` headers once V2 ships). Breaking changes inside v2 are forbidden after release; additive changes are fine |
| Concurrency | List representations carry `ETag: "r{head_revision}"`. Content writes accept `If-Match` (412 on mismatch). **Restore and sync require it** (428 if missing) |
| Idempotency | `Idempotency-Key: <uuid>` is accepted on create list, create link, fork and branch (stored as `creation_key`). It is **required** on sync apply ([08](08-SYNCHRONIZATION-SPEC.md#identifiers-fingerprints-and-idempotency)) |
| Rate limits | DRF scoped throttles keyed by user id when signed in and by client IP otherwise, stored in the PostgreSQL DatabaseCache with V1's advisory-lock fix. Reads aren't throttled except directory search |
| Errors | DRF's shapes (V1-compatible: `{"detail": …}` or `{field: [messages]}`) plus a stable machine `code` |

### Error format

```json
{"detail": "The source list changed while you were reviewing.", "code": "stale_preview", "fingerprint": "…"}
{"destination_url": ["This URL is already in the list."], "code": "invalid"}
```

Domain code raises framework-free exceptions that subclass the categories in
`apps/common/errors.py` (for example `versioning.domain.errors.StalePreview(Conflict)`).
`config/exceptions.py`, the DRF `EXCEPTION_HANDLER`, maps them to a status through the class
hierarchy and adds `code` (plus any extra fields, such as `fingerprint`) to every error body
under `/api/v2/`. V1 bodies keep their exact V1 shape. Services written in V1 style that raise
DRF exceptions stay valid until touched. Infrastructure errors (DB timeouts, lock timeouts)
map to 503 `temporarily_unavailable` with `Retry-After`, never to raw 500 text.

| Domain error | HTTP | `code` |
|---|---|---|
| `NotVisible` | 404 | `not_found` |
| `Forbidden` | 403 | `permission_denied` |
| `AuthenticationRequired` | 401 | `not_authenticated` |
| `Expired` | 410 | `gone` |
| `RevisionMismatch` | 412 | `revision_mismatch` |
| `PreconditionRequired` | 428 | `precondition_required` |
| `StalePreview`, `ParentUnavailable`, `NotABranch`, `Conflict` | 409 | as named |
| `InvalidDecisions`, `LinkLimit`, `DuplicateUrl`, `IdempotencyKeyReused`, validation | 422 or 400 | as named (field errors stay 400, as in V1) |
| `RateLimited` | 429 | `throttled` + `Retry-After` |
| `Unavailable` (since 9.0: the mail relay failed while sending a report) | 503 | `unavailable` |

## URLs and slugs

- The canonical list URL is `/l/{code}/{slug}`, where the slug is cosmetic and ignored when
  resolving. `/l/{code}` alone keeps working forever (V1 links). The SPA rewrites the address to
  the current slug. The slug is regenerated from the title unless the owner edits it.
- Reserved second segments: `manage` (the V1 edit link `/l/{code}/manage#t=`), `history`,
  `sync`, `settings`. Slugify appends `-list` if a title would produce one of these.
- Group URL: `/g/{code}/{slug}`. Group context for a list: `/g/{code}/l/{listCode}`.
- Short link redirect: `/r/{code}` (V1, unchanged except for the visibility rule).

## Session and account

Authentication flows use **django-allauth headless, browser client**: `/_allauth/browser/v1/…`
[R6]. The SPA uses `POST auth/login`, `POST auth/signup`, `DELETE auth/session` (sign out),
`POST auth/password/request`, `GET`/`POST auth/password/reset` (GET checks a key sent as
`X-Password-Reset-Key`), `POST auth/email/verify`, `PUT account/email` (resend verification;
**403 means nothing was sent**, because one went out recently or the address is verified) and
`POST account/password/change`. **A 401 from sign-out, password reset or verify-while-signed-out
means the step succeeded and left the browser signed out.** Errors are
`{status, errors: [{message, code, param}]}`. The project adds:

| Method | Path | Notes |
|---|---|---|
| GET | `/api/v2/session/` | Sets the CSRF cookie. Returns `{user: {id, email, display_name, email_verified} \| null}` |
| GET | `/api/v2/me/` | The signed-in user (401 when signed out) |
| PATCH | `/api/v2/me/` | `display_name` (≤80 characters, trimmed). `email` is read-only here; changing it goes through allauth's verified flow |
| DELETE | `/api/v2/me/` | Account deletion. Requires `{"confirm": "<email>"}` (case-insensitive; otherwise 400 on `confirm`). 204: every session ends, owned lists are hidden at once, and everything is erased after 30 days ([ADR-016](adr/ADR-016-account-deletion-grace-period.md)). `deletion_scheduled_for` appears on the session's user while it can still be restored |
| POST | `/api/v2/me/restore/` | Undo the deletion within the 30 days (the session of a deleting account works only here and on `GET /api/v2/session/`). 200 → the account; 409 once erased |

## Lists

| Method | Path | Who | Notes |
|---|---|---|---|
| GET | `/api/v2/lists/` | signed in | Lists the user owns or is a member of. `?role=owner\|editor\|viewer`, `?q=`, `?ordering=-updated_at\|title` |
| POST | `/api/v2/lists/` | signed in | `{title, description?, visibility?, expires_at?}` → 201 + revision 1. `Idempotency-Key` optional |
| GET | `/api/v2/lists/{code}/` | can view | Detail (below). `ETag` |
| PATCH | `/api/v2/lists/{code}/` | editor (content) / owner (settings) | Content fields write a revision; settings don't |
| DELETE | `/api/v2/lists/{code}/` | owner, legacy token | 204. Hard delete |
| POST | `/api/v2/lists/{code}/claim/` | signed in + `Authorization: Bearer <token>` | Makes the caller owner and retires the token (atomic). 200 → detail |
| POST | `/api/v2/lists/{code}/rotate-token/` | legacy token | `{owner_token}` (V1 behaviour) |
| PUT, DELETE | `/api/v2/lists/{code}/image/` | editor, owner (an account: not the edit link) | multipart `file` ≤2 MB → re-encoded to fit 512×512 ([ADR-012](adr/ADR-012-media-and-images.md)). PUT 200 → detail with `image_url`; DELETE 204 |
| GET, POST | `/api/v2/lists/{code}/members/` | owner (editors may read; viewers 403). Session only | POST `{email, role}` with role `editor` or `viewer` → 201. The owner needs a verified email (403 `email_unverified`), and so does the added account: unknown and unverified addresses get the same 400 on `email`. Rate limit `member_add` |
| PATCH, DELETE | `/api/v2/lists/{code}/members/{user_id}/` | owner; members can DELETE themselves (leave) | PATCH `{role}` → 200. DELETE → 204. The owner can't leave (403) |

A member is `{user_id, display_name, email_hint, role, added_at, is_you}`. `email_hint`
(`b…@example.com`) tells people apart without showing the address ([12](12-AUTHORIZATION.md#leak-analysis)).


List detail:

```json
{
  "id": "550e8400-…", "code": "X7pKm2Qv8Nw4Rs6A", "slug": "dev-tools",
  "url": "https://go.example.com/l/X7pKm2Qv8Nw4Rs6A/dev-tools",
  "title": "Dev tools", "description": "", "image_url": null,
  "visibility": "unlisted", "allow_fork": true, "allow_branch": false, "tags": ["dev"],
  "owner": {"display_name": "Theo"}, "legacy": false,
  "created_at": "…", "updated_at": "…", "expires_at": null,
  "head_revision": 14, "link_count": 12,
  "my_role": "owner", "permissions": ["view", "view_history", "edit", "upload", "settings", "view_members", "members", "delete", "fork", "branch"],
  "origin": {"kind": "branch", "parent": {"code": "…", "title": "Team tools"}, "sync": {"state": "updates_available", "behind": true}}
}
```

`permissions` comes from the policy, so the UI never re-derives rules. `owner` is present
only when the viewer may see it ([12](12-AUTHORIZATION.md#leak-analysis)). `origin` is
null for ordinary lists. `parent` is null when the viewer can't view the parent.

Since task 5.1 `origin` is `{"kind": "fork", "parent": {"code", "title"} | null}` for a copy
(the `branch` kind and `sync` are postponed). `parent` is null when the source was deleted,
has expired or isn't viewable to the reader *now*, so a copy never reveals a list its reader
can't open. It is in every list representation (detail, My lists, a group's lists), resolved
with one query per response (`selectors.fork_sources`).

## Links

| Method | Path | Who | Notes |
|---|---|---|---|
| GET | `/api/v2/lists/{code}/links/` | can view | Live links by `position` (page size 100) |
| POST | `/api/v2/lists/{code}/links/` | editor, legacy | `{destination_url, title?, description?, position?}` → appended unless `position` is given. Creates the short URL and enqueues metadata |
| PATCH | `/api/v2/lists/{code}/links/{id}/` | editor, legacy | `title`, `description`, `destination_url`. The `id` and short URL are preserved (K1) |
| DELETE | `/api/v2/lists/{code}/links/{id}/` | editor, legacy | 204. Tombstone |
| POST | `/api/v2/lists/{code}/reorder/` | editor, legacy | **Move** semantics: `{"link": "<uuid>", "to_index": 3}` (clamped, 0-based among live links). Moving to the same index is a no-op. Concurrent moves serialize under the lock, so none is lost. 200 → the live links in their new order. A deleted or foreign link → 404 |
| POST | `/api/v2/lists/{code}/links/{id}/move-to-list/` | editor of both lists | `{"list": "<target code>"}`. Copy + tombstone (K4), appended to the target. The new link gets a new short URL; the old one answers 404. 201 → the new link. A target you can't see → 404, can't edit → 403; the same list, a full target or a duplicate URL there → 400 and nothing changes. Both lists are locked in ascending id order |
| PUT, DELETE | `/api/v2/lists/{code}/links/{id}/icon/` | editor, owner (an account) | multipart `file` ≤2 MB, re-encoded to fit 128×128. PUT 200 → the link with `icon_url`; DELETE 204. A deleted link → 404. Versioned (from 3.2) |
| POST | `/api/v2/lists/{code}/links/{id}/refresh-metadata/` | editor | 202. At most once per hour per link |

Since task 2.1 the links list, create, update and delete endpoints return live links in
their stored order with `description`, `position` and `source_link_id`. Delete keeps a
tombstone, and its short URL answers 404. Create takes an optional `position` (clamped)
and `Idempotency-Key` (a retry answers 200 with the first link). PATCH can't change
`position`: that is the reorder endpoint (2.2). `icon_url` (the uploaded icon) is there since
2.3, and `display` since 2.4 (until 7.3 fills `metadata`, it holds the user's values and the host);
`metadata_status` follows in 7.3. The V1 API keeps its representation and newest-first order, and
deletes as tombstones too.

Link representation (V1 fields kept, new fields added):

```json
{
  "id": "8f6d…", "destination_url": "https://example.com/article", "short_url": "https://go.example.com/r/Ab3Kp7Nq2Wz8Lm5R",
  "title": "Interesting Article", "description": null, "icon_url": null, "position": 0,
  "display": {"title": "Interesting Article", "description": "From the page…", "icon_url": "/media/meta/2b9e….webp", "site_name": "Example"},
  "metadata_status": "ready", "source_link_id": null, "created_at": "…", "updated_at": "…"
}
```

Since task 7.3: `metadata_status` and `fetched` (`{title, description, icon_url, site_name}`
or null: what the page itself says, offered as suggestions and never copied into the link's
fields) are in the representation. Fetched values count only when they were fetched for the
link's **current** URL; after a URL change the link is `pending` again and shows the host.
`refresh-metadata` answers 202 and queues a fetch, 429 with `Retry-After` within an hour of
the last one, 409 `metadata_disabled` when fetching is off, 404 for a deleted link; it needs
edit rights. Fetches are queued on create, on a URL change, and for restored, moved or copied
links whose stored metadata is for another URL.

`display` applies the precedence rule user > fetched > fallback, so clients don't reimplement
it: `title` = title, else the fetched title, else the host (lowercase, no `www.`, punycode kept);
`description` = description, else the fetched one, else null; `icon_url` = the uploaded icon,
else the fetched one, else null (the client then draws the letter avatar); `site_name` = the
fetched site name, else the host. `metadata_status` is one of `pending`, `ready`, `unavailable` or `disabled`.

## Revisions and restore

| Method | Path | Who | Notes |
|---|---|---|---|
| GET | `/api/v2/lists/{code}/revisions/` | editor, owner, legacy | Newest first: `{number, kind, created_at, author: {display_name} \| "edit link" \| null, summary, restored_from}` |
| GET | `/api/v2/lists/{code}/revisions/{number}/` | same | `{…summary fields, snapshot, diff_from_previous}` (snapshot rendered with link labels) |
| POST | `/api/v2/lists/{code}/restore/` | editor, legacy | `{"revision": N}`. `If-Match` **required**. 200 `{revision: new head, changed}` |

Since task 3.3:

- The history is paginated (20 per page) and carries the list's `ETag`. `author` is
  `{display_name}`, `"Deleted account"` as the name of an account being deleted or erased
  ([ADR-016](adr/ADR-016-account-deletion-grace-period.md)), `"edit link"` for a V1 edit
  link, or `null` for a `migrated` baseline. Viewers, strangers and anonymous callers get
  403/401 (404 for lists they can't see at all).
- `diff_from_previous` is `{list: {field: {before, after}}, links: [{id, url, title, changes,
  position_before, position_after, fields}]}`; `changes` is a subset of `added`, `removed`,
  `modified` and `moved`, and `fields` holds `{before, after}` per changed field. Links are
  in the revision's order, removed ones last. Revision 1 has an empty diff.
- Restore without `If-Match` is 428 `precondition_required`; with a stale one 412. Restoring
  content equal to the head writes nothing (`changed: false`). Its rate limit is `restore`
  (120/h, `THROTTLE_RESTORE`).

## Groups

| Method | Path | Who | Notes |
|---|---|---|---|
| GET, POST | `/api/v2/groups/` | signed in | Groups the user owns or is a member of / create |
| GET, PATCH, DELETE | `/api/v2/groups/{code}/` | per [12](12-AUTHORIZATION.md#group-permission-matrix) | |
| GET | `/api/v2/groups/{code}/lists/` | can view the group | **Only the lists this viewer may see**, in order. Each item is a list summary |
| POST | `/api/v2/groups/{code}/lists/` | group editor + share right on the list | `{"list": "<code>"}` → appended. Duplicate → 409 |
| DELETE | `/api/v2/groups/{code}/lists/{list_code}/` | group editor | |
| POST | `/api/v2/groups/{code}/reorder/` | group editor | `{"list": "<code>", "to_index": n}` |
| PUT, DELETE | `/api/v2/groups/{code}/image/` | group editor | |
| GET, POST, PATCH, DELETE | `/api/v2/groups/{code}/members/…` | group owner | As for lists |

Since 4.2. Groups use the session only: a legacy edit link grants nothing on them.

- A group is `{id, code, slug, url, title, description, image_url, visibility, owner,
  created_at, updated_at, list_count, my_role, permissions}`. `url` is `/g/{code}/{slug}`.
  `list_count` counts the lists the group shows **you**. `owner` (a display name) appears on
  public groups and to members. `permissions` come from `can_group`: `view`, `edit`,
  `add_list`, `view_members`, `settings`, `members`, `delete`, `leave`.
- `GET …/lists/` answers a plain array, not a page (a group holds at most 100 lists). Each
  item is a list summary as on `/api/v2/lists/`, as you see that list, plus `shown_to_all`:
  false when you see the list only through your own role on it, so other people who can view
  the group don't. Order is the array's order. Stored positions are never returned
  ([Q17](20-DECISIONS-AND-OPEN-QUESTIONS.md)).
- `POST …/lists/` → 201 with the item. Can't edit the group → 403, checked before anything
  about the list. A list you can't see → 404; one you could see but not share → 403
  `cannot_share_list`; expired → 410; already there → 409 `duplicate_list`; a full group → 400.
- `DELETE …/lists/{list_code}/` and `POST …/reorder/` treat a list hidden from you like one
  that isn't there (404). `to_index` counts only the lists you are shown and is clamped.
  Hidden lists keep their places. Reorder answers with the array.
- `PUT …/image/` as for list images (multipart `file`, 512×512 WebP; `upload` rate limit) →
  200 with the group. Group editors and the owner.
- Members: `{user_id, display_name, email_hint, role, added_at, is_you}`, with the same rules
  and errors as list members.
- Rate limits: `group_create`, `group_manage`, and `member_add` for adding people.

## Directory

| Method | Path | Notes |
|---|---|---|
| GET | `/api/v2/directory/lists/` | `public` only. `?q=` (websearch syntax on title and description [R11]), `?tags=a,b` (AND), `?ordering=-updated_at\|title\|-relevance`. Paginated. Throttled per IP |
| GET | `/api/v2/directory/groups/` | Same for groups |
| GET | `/api/v2/directory/tags/` | Popular tags across public resources (`?prefix=`) |

Since task 8.1:
- Every endpoint answers anyone (session optional), lists **public** resources only, filtered
  in SQL: never unlisted or private ones, expired lists, or those of an owner deleting their
  account. Items are the usual list and group representations (`my_role` for a signed-in
  reader; a group's `list_count` counts only the lists it shows that reader).
- `q` (≤200 characters): web-search syntax over title and description (`simple` config), plus
  partial words in titles (`dock` finds "Docker", through `pg_trgm`). Relevance is the text
  rank (title weighted above description) plus the title's trigram similarity.
- `tags`: comma-separated, normalized like stored tags, all must match. `ordering` defaults to
  `-relevance` with `q`, else `-updated_at`. An invalid value is a 400.
- `/directory/tags/`: `[{tag, count}]`, at most 30, most used first, counting public lists and
  groups only; `?prefix=`.
- Rate limit `directory`, 600/h per IP even when signed in.
- Tags: `tags` in list and group representations and writes (`POST` and `PATCH`; creating
  with tags answered 500 until task 8.2), at most 10, normalized
  (`Dev Tools` → `dev-tools`); owners and editors (`tags` in `permissions`), never an edit
  link; not versioned.

Search inside a list stays client-side (≤100 links, V1 behaviour).

## Moderation

Since task 9.0 ([13](13-SECURITY.md#moderation)):

| Method | Path | Notes |
|---|---|---|
| POST | `/api/v2/lists/{code}/report/` | Anyone who can view the list, signed in or not, except its owner and the holder of its edit link (`report` in `permissions`). `{reason, details?}` → 202 |
| POST | `/api/v2/groups/{code}/report/` | The same for groups: anyone who can view the group except its owner |

- `reason` is `phishing` (phishing or malware), `spam`, `illegal` or `other`; `details` has at
  most 1000 characters.
- As for any request on the resource: 404 when it isn't visible to you, 410 for an expired
  list. 403 for its owner.
- The report emails `MODERATION_EMAIL` at once, from the api. The email names the reporter by
  user id only, never by address or IP, and lists the operator commands that act on it.
  Without `MODERATION_EMAIL` the report is logged, without its details, and still answered
  202. A failing mail relay answers 503 `unavailable`.
- Rate limit `report`: 10/h per user or IP (`THROTTLE_REPORT`).
- The operator has no endpoints: moderation is done with management commands.

## Uploads

Upload endpoints are the only ones above the 16 KB request limit. The request-size middleware
gets a per-route allowance (2 MB plus 64 KB of multipart framing, `UPLOAD_REQUEST_MAX_SIZE`),
and nginx gets a matching `location` with `client_max_body_size 3m`. Everything else keeps the
V1 limits. Since task 2.3:

- The body is `multipart/form-data` with one part, `file`. Other content types answer 415.
- The file is identified by its content (PNG, JPEG, WebP or GIF; never SVG), whatever its name
  or type say. Anything else, or a file over 2 MB or 16 megapixels, answers 400 with a message
  on `file`, and nothing is stored.
- Uploading needs an editor or owner **account** (the policy's `upload` action). An edit link
  gets 403. The rate limit is `upload` (120/h per user, `THROTTLE_UPLOAD`).
- `image_url` and `icon_url` are same-origin paths such as `/media/icons/2b/2b9e….webp`.
  The names are content hashes, so a changed image gets a new URL and caches never go stale.

## Concurrency preconditions

- `ETag: "r{head_revision}"` is sent on list detail and links collections, and on the
  responses of content writes (the new head), since task 3.2. `head_revision` is also in the
  list representation. A 412 body carries the current `head_revision`.
- Comparison is strong: `If-Match: "r12"` or `*`; a weak (`W/…`) or foreign value never
  matches (412). On a list PATCH it applies only when content fields (title, description)
  are changed: settings aren't versioned, so a stale ETag doesn't block them. On
  move-to-list it is the source list's.
- `If-Match` is **required** on restore and sync. It is optional on PATCH/POST/DELETE of
  content: the UI sends it when it shows a form based on a loaded state, and a 412 makes the UI
  reload and re-show the form with the user's input kept.
- Reorder (move) needs no precondition: a move is always applied to the current order.

## OpenAPI

- One schema per version (`SPECTACULAR_SETTINGS` + `?version=`). The cookie/CSRF scheme and
  the legacy `OwnerToken` bearer scheme are both declared. Public reads are marked
  unauthenticated, as V1 tests already assert.
- The frontend's TypeScript types are generated from the v2 schema with `openapi-typescript`
  ([10](10-FRONTEND-ARCHITECTURE.md#api-integration)). CI fails if the generated file is stale.
